# Plan: building 0.2.0

**Done — released 2026-10-15.** Every stage below is built; see the [changelog](../../CHANGELOG.md) for what each delivered and what is still unproven.

How [the 0.2.0 spec](0.2.0-ways-in.md) is built, in stages. Each stage ends with `pnpm -r build`, `pnpm typecheck` and
`pnpm test` green and a commit; the next stage starts from it. Section numbers (§) are the spec's.

**Rules for every stage.** Match the surrounding code: its comment style (why, not what), its naming, its test style
(behaviour, named after what it proves). No behaviour change outside the stage's scope. Every new rule gets a test
that fails without it. Nothing spends money: tests use the fake Claude (`packages/core/test/fake-claude.mjs`), never a
credential. No internal organisation names anywhere (`test/publishing.test.ts` sweeps the build).

## Stage 1 — the engine: runtime, credentials, platforms (`core`, small parts of `github` and `cli`)

1. **`ClaudeRuntime` and `ModelCredential`** (§3.2), in a new `core/src/runtime.ts`:
   `ModelCredential = { kind: 'api-key', value } | { kind: 'oauth-token', value } | { kind: 'claude-login' }`, with
   values wrapped so `String()`, `JSON.stringify` and `util.inspect` print `[redacted]`;
   `ClaudeRuntime = { credential?: ModelCredential; bin?: string; passEnv?: string[] }`;
   `modelCredentialFromEnv(env, { allowLogin })` — refuses `ANTHROPIC_BASE_URL`, refuses both credentials set, returns
   the one set, or `claude-login` when neither and `allowLogin`, else throws (the runner's `assertModelCredential`
   becomes a call to it).
2. **`EngineInput.runtime?`**, carried by `runEngine`, `runCheckPass`, `runRecheckPass` into `spawnClaude`;
   `runReview` takes `runtime?` and puts it on the input. `runtime.bin` wins over `REVIEW_AGENT_CLAUDE_BIN`, and is
   resolved by the same rules (absolute, outside the checkout).
3. **`childEnv(extra, runtime)`**: when `runtime.credential` is given, both ambient credential variables are removed
   and only the given one is set (none for `claude-login`). The allowlist gains `CLAUDE_CONFIG_DIR` and
   `USE_BUILTIN_RIPGREP` (P7). `runtime.passEnv` (P8, §14.13) passes further variables **by name**: names must match
   `^[A-Z_][A-Z0-9_]*$`, and anything starting `ANTHROPIC_`, the two credential names, and the App/record secret names
   are refused. The ambient `ANTHROPIC_BASE_URL` refusal stays (§14.5).
4. **Windows npm installs and the npm stub** (P2): the resolver, finding only `claude.cmd` in an absolute `PATH`
   directory on Windows, looks for `<dir>\node_modules\@anthropic-ai\claude-code\bin\claude.exe`; on every OS a
   candidate under 4 KiB whose text says the native binary is not installed is reported as *"Claude Code's native
   binary is not installed — npm skipped its install script"*, with the fix.
5. **The system prompt through a file** (P3, S8 settled: 2.1.258 accepts `--append-system-prompt-file`): on Windows,
   or whenever the prompt is longer than 16,000 characters, it is written to a fresh `0700` temp directory outside
   the checkout, passed as `--append-system-prompt-file`, and removed after the run.
6. **Finding paths** (P11): after the engine, findings' `file` is normalised — `\` → `/`, a leading `./` dropped, an
   absolute path under the checkout made relative. The review instructions say "a repository-relative path with
   forward slashes"; `REVIEW_INSTRUCTIONS_VERSION` → `1.2.0`, digest updated.
7. **"Outside the checkout"** done right in `engine.ts` (P12), and `shortSkillName` splitting on `/` or `\`.
8. **The skill cache** (P13): created only when skills are configured; default directories per OS — Windows
   `%LOCALAPPDATA%\review-agent\skills`, macOS `~/Library/Caches/review-agent/skills`, Linux
   `$XDG_CACHE_HOME/review-agent/skills` or `~/.cache/review-agent/skills`; the runner's default under the temp
   directory becomes per-user (`review-agent-skills-<uid>`), mode `0700`, and an entry is trusted only if this user
   owns it; write permission restored before removing a staging directory.
9. **Archive entries not written** (P10): node-tar warnings collected (`onwarn`), and paths that collide by case
   (and Unicode normalisation) detected; both listed on the record (`checkout.notWritten`, `checkout.caseCollisions`)
   and named in the summary.
10. **Ctrl-C** (P14): the CLI turns SIGINT/SIGTERM into an abort of the review (a second one exits at once).
11. **Docs**: `docs/security.md` names the variables Windows adds to any child process (P9).

## Stage 2 — one review session (`github`)

1. Move `octokitFor` (with the API-version pin), `pushAccessOf` and `refuseUnbuilt` to `github`. `refuseUnbuilt`
   stops refusing `thorough` (§14.1) and stops refusing `multi` once Stage 3 lands.
2. **`defaultRunReviewDeps({ note, workDir?, skillCacheDir? })`** — the deps the CLI and the runner both wire today.
3. **Reporters** (`github/src/reporter.ts`): `checkRunReporter({ onStarted? })`, `commitStatusReporter()`,
   `noReporter`; `reporterFor(octokit, repo, 'auto' | …)` decides check run vs status with one call to GitHub.
   Status mapping (§14.2): `neutral` → `success` with a description saying it did not run; descriptions clipped to
   140 characters; `target_url` is the summary comment's URL (`upsertSummaryComment` returns it).
   `check-only` mode with a status reporter (§14.3) puts the findings in the summary instead of annotations.
4. **`prepareReview()` and `runReviewSession()`** (§3): the generic part of today's runner — summary-comment lookup,
   re-review questions, deadline and abort, `runReview`, `publishReview`, reporting, the outcome, removing the checkout
   — returning a `SessionResult` and throwing nothing but programmer errors. Neither knows about trigger.dev.
5. **Posting as a person** (§3.3): replies are ignored only from an explicit bot login (§14.6); the summary comment is
   found preferring the same author and a 403 on the edit posts a new one (§14.7); every summary and review body starts
   with the automated-review line (§5.6, §14.9).

## Stage 3 — the multi-reviewer mode (§8.3) (`core`, `github`)

`--multi` (§14.16) with any tier: one engine run per focus (`intent`, `impact`, `security` — the prompt's existing
`REVIEW_LENSES`), each with its own budget (the tier's), partial output kept; a failed focus does not fail the review;
the union goes through one check pass that also marks duplicates (§14.17) — new optional `duplicateOf` in the verdict
schema, duplicates said once; the record gains `focuses: [{ lens, usage, finished, failure }]`; concurrency setting
for local runs; the summary names which focuses ran. Deployment setting `allowMulti` (default `true`; §14.19).

## Stage 4 — the CLI (§5)

`--post`, `--report`, `--re-review`, `--github-host`, `--keep-checkout`, `--yes`, `--multi`; `--version`;
`review-agent doctor`; GitHub token from `GITHUB_TOKEN` → `GH_TOKEN` → `gh auth token --hostname` → offer
`gh auth login --web` on a terminal (§5.3); confirmation before posting (§5.4); exit code 4 (§5.5); `--json` with
`--post` prints `{ record, posted, report }` (§14.8); exactly one model credential, `claude login` when neither
(§14.4).

## Stage 5 — the SDK: `@review-agent/sdk` (§4)

`reviewPullRequest(options) → ReviewResult` over `runReviewSession`, with the options, results, progress events and
concurrency behaviour of §4; a README; published with the other four, at the same version.

## Stage 6 — the App on the session (§6, §8.3.4)

`reviewOnce` becomes: credential and identity, token, `prepareReview`, release-only and push-access gates, close the
remembered check run, `runReviewSession` with a check-run reporter, map the result to the task outcome. Multi-reviewer
reviews fan out to a child task per focus (`review-agent-focus`, `batchTriggerAndWait`, §14.18). `runReviewJob` gets
an `@review-agent/app/runner` export. Every App-facing behaviour and variable unchanged.

## Stage 7 — examples (§7, §14.10, §14.12)

`examples/server/` (receiver + in-process queue + `reviewPullRequest`, App token), its `Dockerfile` (Debian, non-root,
Node 22, Claude Code pinned and verified); `examples/github-actions/review.yml` (the workflow, fork-safe).

## Stage 8 — CI (§12.1)

Unit matrix as today, Windows **required**; a `node:22-alpine` job; a $0 Claude smoke job per OS (pinned Claude Code,
no credential, expect "Not logged in"); Windows fixtures (a planted `claude.exe` never runs; a near-260-character
path; names Windows cannot write are reported).

## Stage 9 — documentation (§11)

The guides of §11, each with numbered steps, the real output to expect, and failures by symptom; PowerShell beside
every shell command; the tier guide (§8); the demo repository `crissmoldovan/review-agent-demo` and the captured
reviews — **paid, and confirmed with the owner before any run (§14.11)**. Spikes S1, S2, S4–S7, S9 run alongside;
S3 (Vercel) needs a Vercel account and is confirmed with the owner too.

## Stage 10 — release

Version `0.2.0` in all five packages, CHANGELOG, migration notes (§13), dry-run, publish, GitHub release.
