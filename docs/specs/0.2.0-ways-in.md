## 0. What changes, in one paragraph

Today there is one way to **post** a review (the GitHub App) and one way to **read** one (the CLI). 0.2.0 makes the
reviewer usable three ways — **the GitHub App**, **the CLI** (now able to post, as you, using your GitHub CLI login),
and **an SDK** you embed, passing in your own keys — all running **one shared review session**, so a review is the
same review whichever way it was asked for. It also defines, tests and documents every place it can run — a laptop on
Windows, macOS or Linux; CI; a VPS or container; Vercel; trigger.dev — and replaces the tier names nobody could choose
between with guidance that says when to use which, and adds a **multi-reviewer mode** — several reviewers, each
looking for one kind of problem, combined into one review. Documentation becomes task-by-task guides with real, captured
output.

## 1. Use cases

Each use case is a promise the docs make and a test the release must pass (§12). "Way in" is the entry point;
"identity" is who GitHub sees posting.

| ID | Who | What they want | Way in | GitHub identity | Model credential | Runs on | Posts |
|---|---|---|---|---|---|---|---|
| **UC-1** | an organisation | every pull request reviewed when it opens; anyone with push access can ask again | App | the App (bot) | API key | receiver anywhere + runner on trigger.dev, a VPS or Vercel Sandbox | review, inline comments, summary, **check run** |
| **UC-2** | a developer | read a review of a pull request before asking a colleague | CLI | none (read only) | API key, subscription token, or `claude login` | their laptop | nothing — prints |
| **UC-3** | a developer | put that review on the pull request | CLI `--post` | **themselves** (`gh` login or a token) | as UC-2 | their laptop | review, inline comments, summary, **commit status** |
| **UC-4** | a repository | review each pull request in GitHub Actions, no App, no server | CLI in a workflow | `github-actions[bot]` (`GITHUB_TOKEN`) | API key (repository secret) | GitHub Actions | review, inline comments, summary, **check run** |
| **UC-5** | a team on another CI | the same from Jenkins, CircleCI, Buildkite… | CLI `--post` | a bot account's token, or an App token they mint | API key | that CI | as UC-3 (status) or UC-1 (check run, with an App token) |
| **UC-6** | a product or platform team | call a review from their own service and do something with the result | SDK | whatever token they pass | API key, passed in | any Node.js 22 process | what they ask for — nothing, or as UC-3/UC-1 |
| **UC-7** | an organisation without trigger.dev | UC-1 on their own server | SDK + receiver, in one process with a queue | the App | API key | a VPS or container | as UC-1 |
| **UC-8** | an organisation on Vercel | UC-1 with the webhook on Vercel | receiver on Vercel + runner elsewhere | the App | API key | Vercel + trigger.dev **or** Vercel Sandbox | as UC-1 |
| **UC-9** | an engineer | review a batch — every open PR, or one PR at several tiers — from a script | SDK | their token | their credential | their machine | usually nothing; the records |

What none of them does: review anything but GitHub pull requests; run the reviewed code; approve or request changes.

## 2. The model behind the use cases

### 2.1 Four independent choices

Every use case is a combination of four choices. The docs teach the choices once, then show the combinations.

1. **Way in** — App, CLI, SDK.
2. **GitHub identity** — what token the review uses. It decides what can be posted (§2.2).
3. **Model credential** — how Claude is paid for (§2.3).
4. **Where it runs** — laptop, CI, VPS, Vercel, trigger.dev; and on which OS (§9).

### 2.2 What each GitHub identity can do

| | App installation token | Actions `GITHUB_TOKEN` | Your `gh` login, or a classic PAT | Fine-grained PAT |
|---|---|---|---|---|
| Read the PR and download the code | ✅ | ✅ `contents: read`, `pull-requests: read` | ✅ `repo` (private) / none (public) | ✅ Contents: read, Pull requests: read |
| Post the review, inline comments, summary, edits | ✅ | ✅ `pull-requests: write` | ✅ | ✅ Pull requests: write |
| **Check run** (with a **Re-run** button) | ✅ | ✅ `checks: write` | ❌ | ❌ |
| **Commit status** (a pass/fail line on the commit) | needs `statuses` permission the App does not ask for today | ✅ `statuses: write` | ✅ | ✅ Commit statuses: write |
| Can a branch rule require it, **pinned to this reviewer**? | ✅ pin to the App | ✅ pin to GitHub Actions | ❌ "any source" only — anyone with push access could set it | ❌ |
| Who the comments are from | the App (bot) | `github-actions[bot]` | **you** | **you** |
| Reach | the repositories the App is installed on, one per review | this repository | every repository you can reach | what you selected |

Sources: check runs — *"Write permission for the REST API to interact with checks is only available to GitHub Apps.
OAuth apps and authenticated users … are not able to create them"*
([docs](https://docs.github.com/en/rest/checks/runs)); fine-grained PATs cannot call the Checks API
([known limitations](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens));
`GITHUB_TOKEN` is an App installation token and `checks: write` lets it create check runs
([docs](https://docs.github.com/en/actions/concepts/security/github_token)); statuses need push access and can be
required, but only checks can be pinned to an integration
([statuses](https://docs.github.com/en/rest/commits/statuses),
[protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)).

**The rule the product applies:** it reports with a **check run** when the token can create one, with a **commit
status** when it cannot, and with **nothing** when asked to (`--report none`). It works out which from the token,
never from a guess about the environment (§5.4).

### 2.3 Model credentials

| Credential | How you get it | Who pays | Allowed for |
|---|---|---|---|
| **API key** `ANTHROPIC_API_KEY` | console.anthropic.com | per-token API prices | **everything** — the only credential for an App, a shared service, or an SDK product serving other people |
| **Subscription token** `CLAUDE_CODE_OAUTH_TOKEN` | `claude setup-token` (one-year token, Pro/Max/Team/Enterprise) | the subscription's allowance | **your own** use: your laptop, your own CI. Never shared across people, never stored by a product |
| **`claude login`** | the Claude Code login on this machine | that account | your laptop only |

Anthropic's terms, quoted so the docs can say it plainly: OAuth is *"designed to support ordinary use of Claude
Code"*; *"Anthropic does not permit third-party developers to … route requests through Free, Pro, or Max plan
credentials on behalf of their users … developers may not collect, store, or intermediate Claude.ai credentials or
session tokens"* ([legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). So:

- the App runner and any shared deployment take **an API key only** (today's rule, kept);
- the SDK takes an API key as the normal path, and passes a subscription token straight to the Claude process without
  storing, logging or reusing it;
- the CLI accepts all three, because it runs as you.

`ANTHROPIC_BASE_URL` stays refused everywhere: the reviewed code goes to Anthropic and nowhere else.

## 3. Architecture: one review session

```
                 ┌──────────── way in ─────────────┐
   GitHub App ── receiver ── runner (trigger.dev / VPS / Sandbox) ─┐
   CLI ───────── review-agent review [--post] ──────────────────────┼──▶  runReviewSession()  ──▶ GitHub
   SDK ───────── reviewPullRequest() ───────────────────────────────┘     (@review-agent/github)
                                                                           │
                                                                           ├─ prepare: PR, base-branch config, settings
                                                                           ├─ engine: review → check → re-check (core)
                                                                           ├─ publish: review, comments, summary, edits
                                                                           └─ report: check run | commit status | none
```

### 3.1 What moves where

| Piece | Today | 0.2.0 |
|---|---|---|
| The review session — prepare, review, publish, report, the deadline, the outcome | inside the trigger.dev runner (`app/src/tasks/review-run.ts`) | `@review-agent/github`: `prepareReview()` and `runReviewSession()` |
| Reporting | check runs only, in the runner | `@review-agent/github`: a `Reporter` — `checkRunReporter`, `commitStatusReporter`, `noReporter` |
| Default dependencies (how to download, where to put the checkout, …) | written twice, in the CLI and the runner | `@review-agent/github`: `defaultRunReviewDeps()` |
| `octokitFor`, `pushAccessOf`, `refuseUnbuilt` | `app` | `@review-agent/github` |
| Model credential rules (`exactly one`, gateway refused) | the runner's `assertModelCredential` | `@review-agent/core`: `modelCredentialFromEnv()`, plus explicit credentials (§3.2) |
| The embeddable entry point | none (`runReviewJob` lives unexported in `app/src/tasks`) | new package **`@review-agent/sdk`**: `reviewPullRequest()` |
| The App runner | everything above, plus App-only steps | the App-only steps — App token, release-only skip, push-access gate, remembering the check run across attempts, trigger.dev retries — then `runReviewSession()` |

`@review-agent/app` keeps the receiver and the trigger.dev tasks. The SDK does not depend on it, so embedding the
reviewer never installs trigger.dev.

### 3.2 Passing the model credential and the Claude binary explicitly

Today the Claude process takes its credential from the host's environment, which an embedding service cannot control
per review (two reviews in one process would race on `process.env`). 0.2.0 adds a **runtime** that travels with each
review:

```ts
type ModelCredential =
  | { kind: 'api-key'; value: string }
  | { kind: 'oauth-token'; value: string }   // a subscription token: passed through, never stored
  | { kind: 'claude-login' }                 // the logged-in Claude Code on this machine
type ClaudeRuntime = { credential?: ModelCredential; bin?: string }
```

- When a credential is given, the Claude process gets **that credential and no other**: any credential variable in the
  host's environment is removed from the child's, so nothing ambient can ride along.
- When none is given, today's rule applies: read from the environment (`modelCredentialFromEnv`), exactly one for the
  App and the SDK, and `claude login` allowed for the CLI.
- `bin` overrides `REVIEW_AGENT_CLAUDE_BIN` per review.
- Credential values are wrapped so that logging, `JSON.stringify` and error messages print `[redacted]`.
- The child's environment is otherwise unchanged: an allowlist, extended per operating system as §9 requires.

### 3.3 Fixes the new ways in need

| Problem (found reading the code) | Fix |
|---|---|
| Replies from whoever **posted** the review are ignored (`threads.ts` treats every author of a reviewer comment as "self"). Posting as yourself would make your own `/dispute` invisible. | Ignore replies only from an explicit identity: the App's bot login, or nothing when a person posted. **(pending §14.6)** |
| The summary comment is found by its hidden marker, whoever wrote it. Two ways in on one PR would edit each other's summary, and a 403 there fails a review that has already been paid for. | Prefer a marker comment by the same login; a 403 on the edit posts a new summary instead of failing. **(pending §14.7)** |
| A review posted under a person's name does not say it is automated. | Every summary and review body says *"Automated review by review-agent"* and how it was run (§5.6). **(pending §14.9)** |
| Nothing deletes a review's checkout. Harmless in a short task; a long-running VPS service fills its disk. | The session removes the checkout when it finishes, unless asked to keep it (`keepCheckout`). |
| `--post` refused, no `--version`. | §5. |

## 4. The SDK — `@review-agent/sdk`

### 4.1 The one call

```ts
import { reviewPullRequest } from '@review-agent/sdk'

const result = await reviewPullRequest({
  repo: 'acme/api',
  pr: 128,
  github: { token: process.env.GITHUB_TOKEN! },           // or { octokit }
  credential: { apiKey: process.env.ANTHROPIC_API_KEY! },  // or { oauthToken } or 'claude-login'
  post: true,                                              // default false: review and return, post nothing
})

if (result.kind === 'reviewed') {
  console.log(result.record.costUsd, result.findings.length, result.report?.conclusion)
}
```

### 4.2 Options

| Option | Type | Default | What it does |
|---|---|---|---|
| `repo`, `pr` | `'owner/name'`, number | required | the pull request |
| `github` | `{ token: string, baseUrl?: string }` \| `{ octokit: Octokit }` | required | how to reach GitHub. `baseUrl` for GitHub Enterprise Server |
| `credential` | `{ apiKey }` \| `{ oauthToken }` \| `'claude-login'` | from the environment, exactly one | the model credential (§2.3) |
| `post` | `boolean` | `false` | post the review, comments and summary |
| `report` | `'auto'` \| `'check-run'` \| `'commit-status'` \| `'none'` | `'auto'` | how to report the outcome on the commit (§2.2). `'check-run'` with a token that cannot create one is an error before any money is spent |
| `tier`, `effort`, `model`, `check`, `brief`, `budgetUsd` | as the CLI flags | the deployment's | this request: `model` is the model's name, e.g. `claude-opus-5` |
| `settings` | `Partial<DeploymentConfig>` | built-in defaults | the deployment settings ([configuration](../configuration.md)) |
| `authorize` | `(who) => Promise<boolean>` | none | a gate before any money is spent, e.g. `pushAccessOf` |
| `claude` | `{ bin?: string }` | `REVIEW_AGENT_CLAUDE_BIN`, else `claude` on `PATH` | which Claude Code to run |
| `workDir` | absolute path | the OS temp directory | where checkouts go; removed after each review |
| `skillCacheDir` | absolute path | per OS (§9) | where skills are cached |
| `deadlineMs` | number | 30 minutes | the review stops itself after this |
| `signal` | `AbortSignal` | none | cancel it |
| `onProgress` | `(event) => void` | none | `{ stage: 'preparing' \| 'downloading' \| 'reviewing' \| 'checking' \| 'rechecking' \| 'publishing', … }` |

### 4.3 Result

```ts
type ReviewResult =
  | { kind: 'reviewed'; record: ReviewRecord; findings: Finding[]; posted: PostedSummary | null
      report: { kind: 'check-run' | 'commit-status'; conclusion: 'success' | 'failure' | 'neutral'; url: string | null } | null }
  | { kind: 'unfinished'; record: ReviewRecord; reason: string }     // the model ran but produced nothing usable
  | { kind: 'refused'; reason: string }                              // `authorize` said no — nothing spent
  | { kind: 'failed'; stage: 'before-model' | 'model' | 'withheld' | 'publish'; reason: string; spentUsd: number }
```

The SDK **returns** outcomes rather than throwing them, so a host can tell "the reviewer found nothing" from "the
reviewer did not run" (they are not the same, and a well-formed empty list is success). It throws only for programmer
errors: a missing required option, an option of the wrong type.

### 4.4 Concurrency and lifetime

- Reviews in one process run concurrently and share nothing but the skill cache.
- Each review gets its own checkout under `workDir`, removed at the end (also on failure and on abort).
- The SDK starts no server, keeps no state between calls and stores nothing. A host that wants a queue, retries or a
  record store builds it around the call — §7 shows one.

## 5. The CLI

### 5.1 Commands

| Command | Status | What it does |
|---|---|---|
| `review-agent review` | changed | reviews a PR; **`--post` now posts**, as the token's identity |
| `review-agent doctor` | **new** | checks this machine: Node, the Claude binary (and that it is not npm's stub), its version, which model credential is in use (by name, never value), `ANTHROPIC_BASE_URL`, the GitHub token's source and what it can do on a given repository |
| `review-agent init` | unchanged | registers a GitHub App |
| `review-agent --version` | **new** | prints the version |

### 5.2 New and changed `review` flags

| Flag | Default | What it does |
|---|---|---|
| `--post` | off | post the review, inline comments and summary, and report on the commit |
| `--report auto\|check-run\|status\|none` | `auto` | how to report the outcome (§2.2) |
| `--re-review` | on with `--post` | read the reviewer's earlier summary on this PR and run the re-review pass |
| `--github-host <host>` | `github.com` | GitHub Enterprise Server |
| `--keep-checkout` | off | keep the downloaded code for inspection, and print where |
| `--yes` | off | do not ask for confirmation before posting (always on when there is no terminal) |

`--json` with `--post` prints `{ "record": …, "posted": …, "report": … }` instead of the bare record.
**(pending §14.8)**

### 5.3 Where the GitHub token comes from, in order

1. `GITHUB_TOKEN`, if set and not empty;
2. `GH_TOKEN`, if set and not empty;
3. **`gh auth token --hostname <host>`**, if the GitHub CLI is installed and logged in;
4. otherwise: with a terminal, offer to run `gh auth login --web` for you (it opens a browser and you approve there);
   without one, exit `2` saying exactly which of the above to set.

The token is never printed, logged, put in the Claude process's environment or written to disk.

### 5.4 Posting as yourself

- Before posting the CLI says, once, what it will do: *"This will post as @alice on acme/api#128: a review with
  inline comments, a summary comment and a commit status 'review-agent'. Continue? [y/N]"*. `--yes` skips it.
- `--report auto` picks a check run when the token can create one (an App or Actions token), otherwise a commit status.
  It finds out with one call to GitHub, not by guessing.
- A commit status is **a soft gate**: a branch rule cannot pin it to this reviewer, so anyone with push access could
  set one with the same name. The docs say so wherever they mention it.
- A run interrupted after setting `pending` (Ctrl-C) sets the status to `error` on the way out, so it does not block
  a merge forever; a later run with the same name replaces it.

### 5.5 Exit codes

| Code | Meaning |
|---|---|
| `0` | reviewed (and, with `--post`, posted) |
| `1` | the review did not finish |
| `2` | bad usage, or something missing before the review starts: flag, token, credential. *(A missing Claude binary is found when the review starts it, and exits `1` — corrected 2026-10-15 to match the code; `review-agent doctor` reports it beforehand.)* |
| `3` | the output matched a secret pattern and was withheld |
| `4` | **new**: reviewed and paid for, but posting failed — the review is printed so it is not lost |

### 5.6 What a review posted by a person says

Every summary comment, whoever posted it, starts with one line saying it is automated and how it ran:

> 🤖 **Automated review** by [review-agent](https://github.com/crissmoldovan/review-agent) · run by @alice from the
> command line · tier **basic** · `claude-opus-5` · $0.21 (model spend at per-token API prices)

## 6. The App

No change to what an App deployment does or how it is set up. Inside, the runner calls `runReviewSession()` with a

## 7. Running it yourself — the VPS / container recipe (UC-7)

0.2.0 ships, as **documentation and an example, not a new product surface**:

- `examples/server/` — a small Node.js server: the webhook receiver from `@review-agent/app/receiver`, plus an

## 8. Tiers: what they are and when to use which

### 8.1 What changes

The three tiers stay, are made the same everywhere, and are explained by when to use them rather than by what they
contain. **`thorough` is one reviewer at `high` effort, in every way in (§14.1, taken 2026-10-14).** Breadth — several
reviewers each looking for one kind of problem — is a separate **multi-reviewer mode** (§8.3), not a tier.

| Tier | Effort | Check pass | Soft budget → ceiling | Measured (per-token API prices, `claude-opus-5`) | Use it for |
|---|---|---|---|---|---|
| `basic` | low | on | $2 → $5 | $0.88–1.06, 2–5 min, on real production PRs; $0.16–0.29 on a one-file PR | **every pull request**. The default, and what automatic reviews use |
| `normal` | medium | on | $3 → $7.50 | $1.57–1.67 + check, 4–7 min | a change where a missed bug is expensive: money, auth, permissions, data migrations, concurrency, a public API |
| `thorough` | high | on | $8 → $20 | **not measured** — the first captured runs (§11) measure it | the change you would ask your most senior engineer to review line by line: security-critical code, a large refactor, a release branch |

### 8.2 Guidance the docs will give, with examples

- **Start with `basic` everywhere.** Turn it up per pull request, by asking: `/review --tier normal`.
- **A higher tier is not "more findings".** It is more reading before answering. Measured: on one pull request the
  same model found five issues at `low` effort and none at `medium` — one review is a sample. For an important change,
  **two `basic` reviews can tell you more than one `normal`**, and cost about the same.
- **Worked examples** (each with a captured review in the guide, §11):

  | Pull request | Tier | Why |
  |---|---|---|
  | Bump `zod` from 4.6.2 to 4.6.3 | none — skipped automatically (release-only) | nothing to review but a version |
  | Add a field to an API response | `basic` | small, local, easy to check |
  | Change how refunds round amounts | `normal` | money; a subtle bug is costly |
  | Replace the session-token signing scheme | `thorough` | security-critical, every caller affected |
  | A 4,000-line generated client | `basic`, with a `--brief` pointing at the hand-written part | effort spent on generated code is wasted |

### 8.3 The multi-reviewer mode (new in 0.2.0)

**What it is.** Instead of one reviewer looking at everything, several run side by side, each told to look for one
kind of problem — today's prompt already defines three focuses, `intent` (does it do what it says, and correctly),
`impact` (what else it breaks) and `security` — and their findings are combined into one review. A tier still says
**how deep** each reviewer goes; the multi-reviewer mode says **how many perspectives**. They combine:
`--multi --tier normal` is three focused reviewers at `medium` effort.

**When to use it.** A change that is both risky and wide — it touches several areas, or where a single reviewer
tends to spend its whole budget on one kind of problem. Not by default: it costs several reviews.

**What was learned from the only trial** (2026-09-12, three focused `claude-opus-5` reviewers plus a check pass, at
per-token API prices): on one pull request two reviewers finished and found 7 findings (4 confirmed, 2 refuted) for
$2.84, and $2.10 was lost on the third; on another all three were stopped by the ceiling and **returned nothing**,
$5.91. So the design must make a stopped reviewer's work count, and keep one failure from sinking the rest.

**Proposed design** — each point is open until §14.16–§14.19 are taken:

1. **One process per focus**, each with the same read-only rules, its own soft budget and its own ceiling, and its
   partial output **kept** when its ceiling stops it (the engine already keeps partial output on a budget stop).
2. **A reviewer that fails does not fail the review.** The summary says which focuses ran, which were cut short and
   which failed.
3. **Combining** — the union of the reviewers' findings goes through **one check pass**, which already reads every
   finding against the code; it is also asked to mark duplicates, so the same problem found by two reviewers is said
   once. (Alternative: a separate coordinator model run — more cost, one more thing to fail.) **(pending §14.17)**
4. **Running in parallel.** On a laptop, CI or VPS: parallel processes, limited by a concurrency setting. On
   trigger.dev: one review peaks around 400 MiB and the runner's machine has 1 GB, so three side by side do not fit —
   **each focus runs as its own child task** (`batchTriggerAndWait`; a waiting parent is not billed), or the review
   moves to a 2 GB machine. **(pending §14.18)**
5. **Cost and who can spend it.** Roughly the tier's cost times the number of focuses, plus one check pass; the docs
   will carry measured figures from the captured runs (§11). In the App it is **never automatic** and only on request
   by someone with push access; a deployment can switch it off. **(pending §14.19)**
6. **The record** gains one entry per focus — its usage, whether it finished — beside today's single `usage`.

## 9. Environments and operating systems

### 9.1 Support levels for 0.2.0

| | CLI on a laptop | CLI in CI | SDK | App runner |
|---|---|---|---|---|
| **Linux** (glibc, x64/arm64; Debian/Ubuntu containers) | supported | supported | supported | **supported — the only runner platform** |
| **Linux musl** (Alpine) | best effort | best effort | best effort | — |

### 9.2 Per environment

| Environment | Role | What the guide must cover | Limits |
|---|---|---|---|
| **Laptop** (Windows, macOS, Linux) | CLI, SDK scripts | installing Claude Code per OS (native installer recommended; npm 12 needs install scripts allowed, §9.4), `gh auth login`, `review-agent doctor`, the first review, posting | a `gh` token reaches every repository you can (§10) |
| **GitHub Actions** | the CLI in a job | the workflow file; `permissions:` (`contents: read`, `pull-requests: write`, `checks: write`, `statuses: write`); the API key as a secret; installing Claude Code pinned; **fork PRs get no secrets, so the job skips with a message** | 6-hour job limit — not a constraint; a check run belongs to `github-actions[bot]` |
| **Other CI** | the CLI | a bot account's token or an App token; a commit status as the report | a status can't be pinned (§2.2) |
| **VPS / Docker** | receiver + runner in one process (§7) | the Dockerfile (Debian, non-root, pinned Claude Code, binary verified); HTTPS in front; the App key in a file only the service user can read; a per-user `0700` cache directory; `CLAUDE_CONFIG_DIR`, `DISABLE_AUTOUPDATER` | answer GitHub within 10 s, so the queue is required; measured peak ~400 MiB per review (Claude Code documents 4 GB+ RAM for interactive use) |
| **Vercel** | **the receiver** (recommended); the runner only via **Vercel Sandbox** or trigger.dev | the receiver route (as today); handing off to trigger.dev; or starting a Sandbox per review | Functions: Hobby stops at 300 s, Pro at 800 s (1800 s beta); the Claude binary is ~215 MB against a 250 MB bundle limit; `/tmp` is 500 MB; reviews may share an instance; spawning a native binary is **UNVERIFIED** (S3) ([limits](https://vercel.com/docs/functions/limitations)). | **trigger.dev** | the runner (as today) | unchanged; plus self-hosting for data residency | `small-2x` is 1 vCPU / 1 GB; payloads ≤ 3 MB; `maxDuration` counts CPU time, so the review's own deadline is the real stop |

### 9.3 Code changes the platforms need

From a read of the code against each OS (file references are to 0.1.1):

| # | Problem | OS | Severity | Change |
|---|---|---|---|---|
| P1 | **Fixed in 0.1.2.** `spawn('claude')` with the checkout as working directory: **Windows looks in the working directory before `PATH`**, so a pull request that adds `claude.exe` at its root is run instead of Claude, **with the model credential in its environment**. POSIX does the same if `PATH` has an empty or `.` entry. (`cli-process.ts:96`) | Windows (POSIX edge case) | **security — blocks** | Resolve the binary to an **absolute path in the parent**, skipping relative and empty `PATH` entries; refuse one that resolves inside the checkout; `REVIEW_AGENT_CLAUDE_BIN` must be absolute |
| P2 | An npm install of Claude Code on Windows puts only `claude.cmd`/`.ps1` on `PATH`; `spawn` without a shell cannot run them (Node refuses `.cmd` since CVE-2024-27980) | Windows | blocks | The resolver finds `claude.exe` on `PATH`, or the native binary inside the npm package next to a `.cmd` shim, and checks it is not the 500-byte stub. **Never `shell: true`**: no escaping, an 8,191-character limit, and an orphaned Claude on abort |
| P3 | The system prompt and schema travel on the command line; with long deployment and repository instructions this passes Windows' 32,767-character limit | Windows | degrades | Pass them as files (`--append-system-prompt-file`, if the pinned Claude Code has it — S8), in a private temp directory outside the checkout |
| P4 | **Fixed in 0.1.3.** The CLI build's `onSuccess` runs `cp … 2>/dev/null \|\| true`, which fails under `cmd.exe` and copies a file that no longer exists | Windows | blocks (build) | Delete it |
| P5 | **Fixed in 0.1.3** (JS entry points run with Node). Tests execute `fake-claude.mjs` directly (shebang), which Windows cannot | Windows | blocks (tests) | Run `.js`/`.mjs` stand-ins with `process.execPath` |
| P6 | **Fixed in 0.1.3.** Checkouts are never deleted — every CLI review leaves a copy of the reviewed code in the temp directory | all | degrades | Remove in a `finally` (also §3.3) |
| P7 | The child environment drops `CLAUDE_CONFIG_DIR` (relocated logins fail) and `USE_BUILTIN_RIPGREP` (Alpine needs it) | all, musl | degrades | Allowlist both — paths and switches, not secrets |
| P8 | The child environment drops proxy and CA variables, so behind a corporate proxy Claude cannot reach Anthropic | all | degrades | **(pending §14.13)** — `HTTPS_PROXY` can carry a password |
| P9 | On Windows Node re-adds eleven system variables (`SYSTEMROOT`, `USERPROFILE`, `TEMP`, …) to any child; `docs/security.md` says the child sees six | Windows | docs | Document it; none is a secret |
| P10 | Archive entries Windows cannot write (`CON`, `*`, `"`, trailing dots, symlinks without Developer Mode) are **silently missing**; paths differing only by case overwrite each other on macOS/Windows | Windows, macOS | degrades | Record every entry not written, and every case collision, on the record and in the summary |
| P11 | Finding paths: the model may write `src\a.ts` on Windows; case-insensitive matches pass the checkout check but miss the diff | Windows, macOS | degrades | Normalise to repository-relative forward-slash paths when parsing |
| P12 | A skill directory on another drive is treated as inside the checkout (`engine.ts:51`) | Windows | degrades | A correct "is outside" test |

### 9.4 Installing Claude Code — what the guides say

| OS | Recommended | Also works |
|---|---|---|
| macOS | `curl -fsSL https://claude.ai/install.sh \| bash`, or Homebrew | npm |
| Linux | the install script, or Anthropic's apt/dnf/apk repositories | npm |
| Windows | PowerShell: `irm https://claude.ai/install.ps1 \| iex`, or `winget install Anthropic.ClaudeCode` | npm (after P2) |
| CI / containers | npm with the version pinned, then verify the binary (`review-agent doctor`) | the install script |

**npm 12 blocks dependency install scripts by default** ([npm docs](https://docs.npmjs.com/cli/v12/commands/npm-install-scripts)),
and Claude Code's npm package needs its install script to put the real binary in place; without it `claude` is a
500-byte stub that prints *"claude native binary not installed"*. The guides therefore install with scripts allowed for
that one package, and `review-agent doctor` detects the stub (S2 confirms the exact npm 12 behaviour).

## 10. Security, for the new ways in

| Topic | Rule |
|---|---|
| A person's `gh` token reaches every repository they can | It is used only for the one repository named, never stored, never given to the Claude process. `doctor` says what the token can reach. |
| The Claude process can read files | It keeps `--restricted`, `Read/Grep/Glob` and its own working directory. Whether `Read` can reach outside the checkout (for example `~/.config/gh/hosts.yml`) is **UNVERIFIED** and is spike S1 (§12). **If it can, an explicit credential runs the process with a fresh, empty home directory**; `claude login` keeps the real one and the docs say why it is the least isolated choice. |
| Subscription tokens | Passed through, never stored, never shared (§2.3). |
| Commit statuses are spoofable | Documented as a soft gate everywhere (§5.4). For a hard gate, use the App or Actions, whose check runs can be pinned. |
| A person's review looks like theirs | The automated-review line (§5.6). |
| Fork pull requests in Actions | No secrets reach a `pull_request` run from a fork, so the workflow skips with a clear message rather than posting a misleading result. The docs warn against `pull_request_target` for this, which GitHub blocks by default in public repositories from 2026-11-02 ([docs](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)). |

## 13. Versioning and compatibility

0.2.0. Nothing an App deployment configures changes. For the CLI, `--post` changes from "always refused" to "posts",
